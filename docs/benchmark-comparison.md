# External sorting benchmark comparison

## Goal

This benchmark compares the historical recursive external-sort implementation with the bounded multi-pass implementation introduced in commit `1fe76cd`.

The legacy baseline is preserved only in [external_sort_benchmark_test.go](../external_sort_benchmark_test.go). It is a test-only copy of the algorithm from the parent revision (`f18bf6a`), so it cannot be called by the application. A unit test checks that it still produces one record per input query for the benchmark fixture.

## Scenario

- Dataset: `unique-4096-v1`, generated by `writeBenchmarkInput` in [external_sort_benchmark_test.go](../external_sort_benchmark_test.go).
- 4,096 unique, single-word queries; every query occurs once.
- `--n=64`.
- The fixture deliberately has more unique values than the memory limit. It is the worst relevant case for the old algorithm: it recursively rewrites the remaining input after every group of 64 unique queries.
- The benchmark measures complete processing, including temporary files and final output. Fixture creation and log output are excluded from timing.

Run it with:

```bash
make benchmark
```

The Make target executes each sub-benchmark five times with `-benchmem`.

## Dataset: `unique-4096-v1`

The fixture is deterministic rather than stored as a generated file. It contains one newline-terminated query per line:

```text
query-000000
query-000001
...
query-004094
query-004095
```

| Property | Value |
| --- | --- |
| Records | 4,096 |
| Unique queries | 4,096 |
| Occurrences per query | 1 |
| Memory limit | 64 unique queries |
| File size | 53,248 bytes |
| SHA-256 | `71d0d9d87295006b71729cb9a94f8ce0088b1c49cd6258ee4605bbdbadc7b4c3` |

The SHA-256 is calculated over the exact UTF-8 bytes generated by the benchmark: `query-%06d\n` for every integer from 0 through 4,095 inclusive.

## Measurements

Measured on 2026-08-08 with Go 1.25.5, macOS on Apple M1 Max (`arm64`). The table shows the median of five runs; absolute values depend on the filesystem and host.

| Implementation | Median time | Allocated bytes/op | Allocations/op |
| --- | ---: | ---: | ---: |
| Historical recursive batches | 306.5 ms | 3,564,224 | 155,936 |
| New bounded merge | 24.8 ms | 3,696,993 | 69,453 |
| Difference | **12.3× faster** | 3.7% more | **55.5% fewer** |

Raw `ns/op` values:

| Implementation | Five runs |
| --- | --- |
| Historical recursive batches | 307,569,208; 307,148,312; 304,862,094; 306,353,292; 306,479,021 |
| New bounded merge | 26,061,227; 26,357,977; 24,242,656; 24,551,285; 24,832,321 |

The new implementation makes slightly more byte allocations because it uses CSV-compatible TSV encoding and atomic output replacement. It still allocates far fewer objects and, more importantly, eliminates the repeated whole-file spill passes.

For this fixture, the old algorithm writes 129,024 records into successive spill files before its final merge. The new pipeline creates bounded sorted runs, aggregates them once by query, and performs a bounded merge by frequency. This changes the dominant intermediate I/O from quadratic in the number of unique queries divided by `N` to multi-pass merging with fixed fan-in.

This is a targeted stress benchmark, not a claim that every input is 12.3× faster. Re-run it after performance-sensitive changes and compare the distributions rather than relying on a single run.
